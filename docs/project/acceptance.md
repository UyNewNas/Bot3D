- 更新日期：2026-11-23
- 当前事实：产品验收全部 PENDING；没有产品闸门通过记录，没有指定现实验收者
- 权威范围：本文件定义闸门、证据规则与记录索引；实际运行和判定只在对应 AR 保存
- 关联：[需求与追踪矩阵](requirements.md)、[开发台账](backlog.md)、[测试计划](test-plan.md)

## 1. 判定原则

1. 以“REQ / AC 断言＋闸门＋环境＋子场景＋版本”核对证据，不按文档页数或完成任务数量验收。一个 AC 中的多条断言必须分别有依据。
2. 技术检查结果与产品验收分列。DOC 检查可以 PASS，但不代表产品测试通过、用户定版或现场批准；执行者不得替未指定的验收者签收。
3. 本轮必测全部 PASS、交付物与复现说明齐全、阻断缺陷关闭，且指定验收角色给出判定后，产品闸门才可 PASS。任何必测 FAIL / BLOCKED / SKIPPED / NOT_RUN 都不得放行。验收缺少指定角色或尚未审查时为 PENDING；明确无法取得必需环境 / 授权时登记 BLOCKED 及解除条件。
4. 迭代只验选定切片。G-I01 不等于 G-M1；阶段切片通过不等于跨阶段需求 ACCEPTED。整条需求须闭合矩阵中的首次与必须复验闸门，并注明适用环境。
5. 失败保留原 AR 与 DEF；修复后新增 AR，引用原缺陷并回归。不得覆盖原输出、删除失败或将 UNKNOWN 改写成历史成功。事实订正追加说明，不抹除旧记录。
6. 范围、公共语义、成功阈值或必须环境发生变化，登记 CHG、原因、决策者、影响与回归集合。未批准的变更保持待决，不用缩小测试集合让原范围“通过”。

## 2. 准入与闸门定义

所有产品闸门共同要求：已选择迭代和 AC 切片，依赖满足；代码 / 配置 / 数据版本可定位；测试参数与成功阈值已锁定；执行、复核、验收职责明确；有恢复方案。开发前置依赖不自动授予外部连接、安装、采购、Git 发布或硬件操作权限。

## 3. 阶段必测集合与累计规则

以下是最低集合；每轮开始时在迭代 / AR 中展开环境和子场景，不把编号范围当作一次批量执行命令。新风险或缺陷需要增加回归，不允许删减原 AC。

- **G-I01**：按 [I01](iterations/I01-M1-foundation.md) 的十个 UNIT / MOCK 切片与 DOC 设计评审验收。T31 / T34 本轮只要求测试设计，不记作产品用例 PASS。
- **G-I02**：T01—T08、T10 / T11、T14、T16 的纯时钟切片、T18 的注入切片、T23、T27、T29—T31、T33、T42，以及 T06 对应的状态投影；T02 / T03 此时仅验证 JournalPort / 内存替身语义。完整恢复、持久性和跨进程证据留在 I03 / G-M1。
- **G-I03 / G-M1**：累计 T01—T18 的 UNIT / MOCK 切片、T23、T26—T35、T41—T43、T46；T09 必含 SQLite 的实际子进程终止与重启，不只抛异常；T18 区分注入、存储不可写和日志阻塞。T21 的内存基础用 T32 验，真正 WS 留 M3；T19 / T20、T22、T24 / T25 不混入 M1 的已通过集合。
- **G-M2**：G-M1 回归；在锁定 ROS / SIM 中复验矩阵适用断言，特别是 T05—T14、T16—T20、T23、T27、T29、T31 / T33 / T34、T35、T41—T43、T45 / T46。T20 是实际执行链冲突检查；T16 含真实仿真 pause / resume / step / reset。T15 / T28 保留数学回归，不宣称头显已验证。
- **G-M3**：保留 G-M2 基线；T02—T07、T17、T21—T23、T26—T33、T35 / T36、T41—T43 中所有适用网关 / 前端切片，含真实断线、游标续接、停止独立授权和跨主机连接；T15 / T28 含所选头显坐标与跟踪失效；T27 / T30 含桌面和头显完整 SIM 任务。
- **G-M4**：核对矩阵要求的 G-M4 复验项；T06 / T19 / T22 / T25 / T41 / T43 支撑只读准入；T07 / T10 / T11 / T24 / T25 / T31 支撑本地停车与旧执行者处置；T27 / T37 支撑同机器人迁移。仅运行经批准且适合该设备的故障场景；未获准必验项保持未闭合，不照搬仿真脚本。
- **G-M5**：T27 / T38 与 T23 / T27 / T39 分别支撑第二仿真器与第二机器人；复验矩阵中对该环境适用的断言。迁移切片可分别积累，阶段整体不能因一个切片成功就 PASS；SIM-only 机器人验证不能称为硬件迁移成功，REAL 仍需对应授权和证据。
- **G-EXT**：仅在范围获选后锁定第二 XR 或媒体切片；不借扩展重新定义已验收的命令语义。

一个版本的通过只适用于所记录环境。更换驱动、模型、标定、规划参数、前端或保护机制后按影响分析复验。累计证据引用原 AR 和具体子场景；不能只引用上次“阶段通过”的标题而省去原始证据。

## 5. 每轮记录模板

在 records/ 新建下一个 AR 文件；下列围栏是模板，不是已经执行的记录。一次实际验证失败后修复复验，必须新建下一 AR，不把旧 FAIL 改为 PASS。执行尚未开始可先建 PENDING 记录，再追加该次实际输出；运行后的更正保留原结果。

```markdown
# AR-NNNN：本轮标题

- 日期、迭代 / 闸门、证据层级：
- 范围：REQ / AC 的具体断言、DEV、测试 ID＋环境＋子场景
- 执行角色 / 复核角色 / 指定验收角色：未指定者明确写未指定
- 技术检查 / 测试结果：NOT_RUN；产品验收：PENDING
- 环境：复现所需的平台、解释器、依赖锁及相关组件版本；设备使用公开样例或脱敏代号
- 版本：提交号或未提交工作树；相关文件校验清单在本地留存
- 参数 / 许可 / 授权 / 准入 / 恢复条件：

## 输入与预期

按子场景列输入、故障点、时钟 / 阈值、预期事件与调用顺序。

## 实际执行

复现命令、退出码、实际结果及预期差异。无输出或未运行时明确说明。

## AC 核对与结论

每个断言给出证据定位、PASS / FAIL / BLOCKED / NOT_RUN；
列已满足与未满足项、已知限制、技术结果和指定验收角色的独立判定。

## 缺陷 / 变更与后续

DEF-NNNN：场景、预期 / 实际、严重性、影响、恢复、修复 DEV 和复验 AR。
CHG-NNNN：原因、原 / 新范围、决策者、状态、影响及必回归集合。
下一任务、权威台账更新和未闭合证据。
```

## 6. 证据管理

- 只保存必要的本地输出；凭据、租约秘密和现实影像不写入共享记录。敏感设备身份可用受控内部代号并保留核验依据。
- 文档 / 代码哈希写清输入文件集合；避免记录文件把自身哈希当作稳定快照。追加记录改变内容后，不能沿用旧哈希宣称它覆盖新内容。
- 原始日志及校验清单按 AR 编号在本地留存。GitHub 的 AR 摘要保留复现命令、退出码、测试结果和验收状态，发布前去掉本机路径、缓存或临时目录及内部审批和执行细节。
- 本地检查器检查格式、链接、JSON、稳定 ID、追踪与依赖；不审定设计语义，不证明业务、持久性、停车或用户验收正确。
