## 1. 约束与设计结论

本设计只细化既有协议，不增加公共命令状态。每个 robot_id 有一个串行协调单元、一个离散业务槽、零个或多个未解决执行锁原因。规划也占槽；没有隐式运动队列；Planner 不执行；外部响应只作为事件回到同一协调序列。

最重要的结论：**最后应用下发裁决不是设备 fencing。**工作线程必须在真正尝试外部调用前回到协调单元作一次性裁决，而不能把排入线程池当作已经获准。即使裁决之后立刻调用 SDK，线程仍可能在两者间被抢占。因此裁决之后就按“可能执行”锁定；STOP 不能凭一次早到的停车反馈解锁，必须解决尚可能迟到的写入，再停止并确认停车。

本文的“持久化成功”是 JournalPort 按已配置事务 / 同步 / 存储假设确认的承诺，不是断电证明。确切 SQLite 模式、事务实现、迁移及保留期由 DEV-M1-10 锁定；在此之前只定义必要顺序和失败策略。没有外部受理原子提交、设备 exactly-once 或硬实时承诺。

## 2. 状态向量与不变量

| 内部量 | 所有者 / 含义 | 不可混淆的事实 |
| --- | --- | --- |
| command_state、result_certainty | 协调单元；使用第 3 节既有枚举 | 业务结论不是当前运动状态，也不是执行锁 |
| business_slot | 协调单元；从接受预留到业务终态，最多一个 | 规划占槽；终态可以空槽但仍有执行锁 |
| execution_blocks | 协调单元；按原绑定 / attempt 保存可能执行、旧写入者、恢复等锁原因 | 不能用一个 active_command=None 丢掉未结执行 |
| binding_snapshot | 不可变 robot / device / backend_kind / epoch / adapter 身份 | 原操作始终指向原绑定对象，不在迟到时重新查“当前后端” |
| dispatch_ticket | 内部一次性许可：command、attempt、绑定、撤销代数、期限、计划与上下文摘要 | 不是公开令牌或设备 fencing；不可复制为第二次外部尝试 |
| revoke_generation | 协调单元的本地撤销代数；失权 / STOP / 失效递增 | 与不可复用 backend_epoch 不同，不要求公开 epoch 按大小比较 |
| actual / quality / time | StateProjection 输入后经协调序列采纳 | 目标、规划、反馈分开；未知不填零，源与接收年龄分开 |
| stop_round / writer_barrier / evidence_revision | 停止、写入闭合及停车证据关联 | STOP 请求回执、线程退出或换 epoch 单独都不等于安全解锁 |

不变量：

1. 新运动必须同时满足：身份 / 绑定 / 权限有效、单写租约与 epoch 匹配、ARMED、能力 / 上下文 / 期限 / 状态合格、业务槽空且 execution_blocks 为空。READY 单独不满足。
2. 每个被接受命令最多一个应用外部执行尝试；同键重试 / 查询、重连 / 重启均不产生第二次 submit。停止重发是停止用例，不是运动重试。
3. 每次外部 execute 必有已确认的接受记录、下发意图和成功的一次性最终裁决；Planner、网关和重放器无绕过入口。
4. 最终裁决先登记 attempt 的“可能执行”锁，再离开协调临界段。外部完成 / 失败不会直接清锁。
5. 已处理的撤销先于最终裁决时，旧 ticket 必拒绝；若裁决先发生，之后任何迟到调用均属于原未结 attempt，必须完成停止与对账，不能当作无事发生。
6. 无法确认不继续推进：日志不健康拒新运动；未知执行保留锁；原绑定无法停车则不切成新可写绑定；无可信反馈不报成功或 STOPPED。

## 3. 命令状态与确定性

以下组合为本轮锁定的实现基线；“确认”只确认该业务结论，不额外证明当前停车。内部 ticket、accept reservation、intent write、writer barrier 都不是新增公共命令状态。

| command_state | 允许的 result_certainty | 业务槽 / 执行锁 |
| --- | --- | --- |
| REJECTED | CONFIRMED | 未接受或确定未下发的接受失败；不得释放其他命令 / 恢复锁 |
| ACCEPTED | PENDING | 占槽；接受记录已确认，尚未规划 |
| PLANNING | PENDING | 占槽；计划就绪仍可留在此状态，无 PLANNED 状态 |
| DISPATCHING | PENDING | 意图已确认；预算已起算；尚未裁决时未必有物理执行，裁决后必有执行锁 |
| EXECUTING | PENDING | 已受理不等于已运动；占槽且锁保留 |
| CANCEL_REQUESTED | PENDING | 取消 / 停止处理中；已可能下发则必须保留锁 |
| SUCCEEDED | CONFIRMED | 后端完成＋新鲜目标误差达标＋停车；关键终态保存后释放业务槽；执行闭合证据另核对 |
| CANCELLED | CONFIRMED | 证明从未下发，或任务取消及停车均确认；不借此消除其他旧执行锁 |
| FAILED | CONFIRMED / UNKNOWN | 确知规划 / 拒绝原因可 CONFIRMED；执行影响不明用 UNKNOWN；终态不自动解锁 |
| TIMED_OUT | CONFIRMED / UNKNOWN | 确知未下发可 CONFIRMED；可能已执行而结果不明用 UNKNOWN；终态不自动解锁 |
| INTERRUPTED | CONFIRMED / UNKNOWN | 不再调度原任务；历史结果是否明确分别记录；终态不自动解锁 |

终态一经对外提交，原 command_state 与该终态的 certainty / 原因不可覆盖。后续原句柄结果、停车证明和恢复处置以关联事实追加；可以解释历史已获更多证据，但不能把原 INTERRUPTED / UNKNOWN 改写为“当时 SUCCEEDED”。公共查询 / 事件的具体扩展字段留网关阶段定义，不通过本设计另造协议状态。

### 3.1 确定性转换表

表中是目标转换；关键记录写入的提交规则见第 5 节。非终态发生未列出的事件时拒绝非法转换并审计，不猜测成成功。重复回调按 attempt / 事件标识去重。

| 当前状态 / 条件 | 串行事件与检查 | 下一状态 / 确定性 | 槽、锁与副作用 |
| --- | --- | --- | --- |
| 无记录 | 新请求非法、无能力 / 权限、忙或过期 | REJECTED / CONFIRMED | 不规划、不下发，不改原命令 |
| 接受预留（内部） | 接受记录写入确认，最终接受条件仍有效 | ACCEPTED / PENDING | 发布接受；预留变业务槽 |
| ACCEPTED | 开始规划 | PLANNING / PENDING | Planner 只规划；槽保持 |
| PLANNING | 规划失败、起点 / 版本无效且本轮不重新规划 | FAILED / CONFIRMED | 已证明未下发；保存结果后释放槽 |
| PLANNING | 有效计划返回 | PLANNING / PENDING | 保存服务端计划 / ResolvedExecution；准备意图，不公开 PLANNED |
| PLANNING | 意图已确认且未撤销 / 失效 | DISPATCHING / PENDING | 起算执行预算，建立内部 ticket；无自动 execute |
| 任意未裁决阶段 | STOP / 取消 / 失权先处理，随后旧计划或意图确认才返回 | CANCELLED / CONFIRMED | 证明该 ticket 不可能再裁决；撤销未下发工作，迟到结果只记事实 |
| DISPATCHING | 最终裁决成功 | DISPATCHING / PENDING | 一次性消费 ticket，先登记执行锁；允许一次原绑定调用 |
| DISPATCHING | 后端明确未受理 | FAILED / CONFIRMED | 记录原尝试拒绝；关闭写入路径，按证据处置锁，不自动重试 |
| DISPATCHING | 原尝试已受理 | EXECUTING / PENDING | 保存原句柄；运动仍取实际反馈 |
| DISPATCHING / EXECUTING | 受理 / 连接结果不能确定，不能继续原处理流 | INTERRUPTED / UNKNOWN | DISARMED，停止与原句柄对账；锁保留，禁止再次 submit |
| DISPATCHING / EXECUTING | 普通取消 / STOP / 失权 | CANCEL_REQUESTED / PENDING | 停止原绑定；STOP 撤租且 DISARMED，普通取消不必撤租 |
| CANCEL_REQUESTED | 已证明取消、写入闭合且可信停车确认 | CANCELLED / CONFIRMED | 记录终态 / 解锁证据后释放相应锁；不自动开始下一任务 |
| EXECUTING | 后端完成但反馈缺失 / 陈旧 / 未停 / 误差不达标 | EXECUTING / PENDING | 不报成功；超时继续适用 |
| EXECUTING | 后端完成且新鲜目标 / 停车及写入闭合均通过 | SUCCEEDED / CONFIRMED | 保存终态，按证据释放该执行锁 |
| 任意非终态 | 接受预留未完成时接受期限失效、B 前下发期限失效，或执行预算到期 | TIMED_OUT / CONFIRMED 或 UNKNOWN | 取决于能否证明未执行 / 已知结果；取消激活、停止，保留未结锁 |
| 任意非终态 | 冷启动接管、绑定 / 关键上下文中断 | INTERRUPTED / CONFIRMED 或 UNKNOWN | 原命令不再调度；新 epoch、撤旧租约、DISARMED，按原绑定对账 |
| 任意业务终态 | 原结果 / STOP 回执 / 反馈迟到，或客户端重试 | 原终态不变 | 只追加关联事实；不复活、不重放；绑定级 STOP 仍可独立处理 |

普通取消先于成功提交时，成功不能越过已处理取消直接发布；完成已提交后再取消，返回原终态，不倒写 CANCELLED。STOP 与原命令是否终态无关，仍对授权的明确绑定执行撤租 / DISARMED / 停止流程。

## 4. 串行裁决、时间和外部隔离

应用层拥有一个 per-robot 协调单元。每个应用操作在同一短临界段内运行到结束，分配 coord_seq；可用单写执行器或同一互斥单元实现，但不得混用两个独立的“状态锁 / 下发锁”而无统一顺序。纯领域不依赖线程、asyncio、磁盘或 SDK。实现选型在 DEV-M1-02 / 08 固化，必须保持下面的语义。

- 所有入口都通过应用操作：接入、租约 / 超时、反馈、规划 / 日志 / 后端结果、最终裁决与快照。外部回调只转换和投递；工作线程不能自行改领域对象。最终裁决也是应用操作，不是 SDK 回调修改状态。
- 临界段内禁止 await、磁盘、规划、SDK、阻塞 join 或等待其他机器人。外部工作只拿不可变快照，在段外执行，结果带原 robot / binding / epoch / command / attempt / generation 返回。
- STOP / 失权有独立有界入口，不等待普通状态队列、日志工作线程或执行线程。它们仍需串行处理；“先”指协调单元实际处理顺序，不承诺按网络到达时间抢占一个已经完成的裁决，不声称硬实时。
- 每次关键操作先按当前单调时间复核租约与期限，不依赖定时器准时回调。时间相同的期限裁决使用半开区间：now < admit_before、now < start_before、now < lease_expiry 才有效；DISPATCHING 起经过时间 >= execution_timeout 即到期。完成事件处理时若预算已经到期，先处理超时，不因反馈源时间更早而追认成功。
- clock_id 必须匹配本次运行；跨度受部署显式限制，admit_before <= start_before。源时间 / 仿真钟不得推进或冻结应用保护钟。时钟不可信拒新运动，但授权 STOP 不依赖其成功。
- 状态质量、静止窗口、目标误差和适配器阻塞预算用显式配置；本轮不发明 REAL 默认安全值。数值由后续 mock / SIM / 设备阶段分别锁定。

READY、ARMED 与 motion_state 独立。解除执行锁不自动授租约 / 激活，也不把 motion_state 填成 STOPPED；可信状态投影自己提供停车事实。身份、上下文、旧写入者保护任一不合格，后续激活仍拒绝。

## 5. 接受、意图、调用和结果的提交顺序

顺序为：鉴权及幂等检查 → 接受预留 → 接受记录确认 → 发布 ACCEPTED → 规划 → 前提复核 → 意图确认 → DISPATCHING / 执行预算 → 最终裁决 → 一次原绑定外部调用 → 受理 / 原句柄记录 → 完成判定 / 终态。关键外部调用不能由日志写入回调自行触发。

### 5.1 接受与幂等

1. 先验证会话 / 资源权限，再查询 robot_id＋command_id。已知同摘要只返回原记录；异摘要冲突，不覆盖旧记录；request_id 仅用于传输关联。
2. 新命令在协调单元内做校验并预留唯一槽 / 幂等键，产生内部 accept reservation；并发同键附着原操作，异键忙则拒绝。预留不是新的公共状态。
3. 段外提交接受记录。记录包含规范化执行摘要、原绑定 / epoch、接受输入与当时检查依据；其物理落盘不独自授予执行权限。写入结果返回同一协调单元后重新检查撤销代数、时钟 / 接受期限、租约、状态与上下文；都满足才发布 ACCEPTED / 允许规划。
4. 若写入完成时已错过接受期限或已经失权，保存接受撤销 / 拒绝结论，绝不发布一个现在仍可继续执行的 ACCEPTED。接受记录里保存的候选事实与公开 ACCEPTED 事件区分；公共查询不把尚未完成应用裁决的 reservation 当作已受理。没有新增公开“接受中”状态，同键请求可有界等待或返回已有 BUSY 类传输错误。
5. 接受写入失败 / 提交结果未知时，不规划、不下发、不伪报持久化成功；冻结相应键并恢复存储对账。不能清空库后把同键当成新命令重做。到期或撤销也要留下原键的结果 / 关联事实；不能用刷新期限变成重试。

“接受完成”的有效时刻是写入确认后，协调单元作最终接受裁决的时刻；写入晚返回不回溯到接收时间。SQLite 后续需能区分接受记录、公开事件与撤销事实；这是私有存储阶段，不增加 command_state。

### 5.2 意图、句柄与终态

- 计划结果带起点、模型 / 场景 / 标定 / 工具 / 能力版本，服务器构造 ResolvedExecution。前提失效首版直接拒绝 / 停止，不自动无限重规划。
- 写意图前检查；意图确认后再检查。STOP 先处理、意图随后才返回时，保留“意图已落盘但已撤销”的事实，不发新 ticket、不调用后端。意图只说明可能准备执行，不是外部受理证据。
- DISPATCHING 的进入时刻取意图确认在协调序列中被接纳的时刻，立即起算执行预算；ticket 等待工作线程也计入，不在收到受理时重置预算。
- intent 中预先保存唯一 attempt / 原绑定 / 可查询原关联标识的策略；外部已受理而句柄尚未保存即崩溃仍可能 UNKNOWN。适配器不能查询原尝试时保持未知，不能换新句柄重试。
- 明确外部拒绝与传输错误不同。后者不能推断未受理。已受理只记录 EXECUTING；必须另有实际反馈和停车才可能成功。
- 终态 / 关键事件按 JournalPort 事务保存后才宣称其持久化。终态写失败时立即禁新运动、取消激活并走停止，不为等磁盘延迟停止；保留待写事实 / 审计缺口，不能伪造已持久化 SUCCEEDED。崩溃后只按实际存储对账。
- 解锁审计独立于停止请求：日志不可写不挡 STOP，但挡住宣称持久化终态与恢复解锁。普通状态可合并，关键事件 / 未结执行不能无声丢失。

## 6. 最后应用下发边界

### 6.1 裁决位置与一次性消费

最后可控边界 B 是执行工作线程已经运行、即将把原 ResolvedExecution 交给外部端口时，调用的应用操作 FinalClaim。不能在“排进线程池 / SDK 自己的普通队列之前”提前消费许可，再把等待中的工作当成不可撤销。若适配器内部仍有可撤销队列，最终检查应下沉到其可控写入入口；端口必须报告仍未闭合的外部提交，不得隐式重试。

FinalClaim 与 STOP / 失权 / 上下文失效使用第 4 节同一协调序列。伪代码仅定义应用语义，不是已实现函数：

```text
FinalClaim(ticket):
  enter per-robot coordination cell; assign coord_seq
  recompute time / lease expiry and all motion prerequisites
  require current command is DISPATCHING and its ticket is unused
  require matching original binding, epoch, generation, plan and intent receipt
  require no cancellation, new execution block or stale prerequisite
  mark ticket consumed; add unresolved attempt BEFORE leaving the cell
  return one-shot InvokeOriginalBinding effect
```

B 的时刻定义为开始向外部端口移交的一次性应用裁决时刻，受 start_before 约束；后端受理或电机启动不在此期限保证内。离开 B 后必须立即尝试端口，不得再放普通执行队列、等待日志、规划或重解析当前绑定。线程抢占与外部传输不是原子操作；超过操作预算或存在不可控长排队的适配方式不得以本设计宣称准时 / 可停止，后续环境准入须验证。

### 6.2 两种排序必须分别处理

- STOP 先于 B：撤销代数 / ticket 在同一序列先变化。即使规划 / 意图结果迟到、工作线程随后苏醒，FinalClaim 仍拒绝，execute 次数必须为零。证明该任务未下发后可结束其业务槽；不能顺便清其他旧执行锁或伪造停车。
- B 先于 STOP：先有可能执行锁。STOP 必须认为原调用可能尚未真正发出、可能已受理、也可能响应丢失；不靠最后一次租约检查或换 epoch 假定阻止了设备动作。请求立即绑定级停止，保持 DISARMED / 物理锁，并执行第 7 节的写入闭合与停车协议。

尤其是 `B → 线程被抢占 → STOP / STOPPED → 旧线程真正调用 SDK`：这是已经越界的未结执行，不是可以忽略的旧反馈。早到的 STOPPED 不足以解锁；若无法证明迟到写入全部消失，就一直锁住。应用 epoch 不会自动阻止这次原设备动作；REAL 的独立本地停车 / fencing 证据仍是准入条件。

## 7. STOP、普通取消与失权

| 入口 | 定位 / 权限 | 对控制权与任务的处理 |
| --- | --- | --- |
| 普通取消 | 原 command_id、绑定与会话权限 | 撤销该任务 ticket；未下发可确认取消；已可能下发进入停止 / 对账。停车且原租约 / 前提仍有效可保留控制权，不自动下一动作 |
| system.stop | 独立停止权限、明确 robot / device / epoch；不要求知道运动 ID 或持运动租约 | 先冻结运动、撤租、DISARMED、递增撤销代数；撤销未下发工作，独立请求原绑定停止；回执只表示请求处理 |
| 失租约 / 到期 / 会话丢失 | 服务端事件，不等客户端主动 cancel | 阻止新运动，DISARMED，对在途请求停止，未结执行处置前不发放新可执行控制流 |
| 超时 / 关键故障 / 关键上下文失效 | 服务端保护事件 | 保守撤销当前运动许可并取消激活；本轮策略同时撤租，停止并保留未结锁；参数变化不暗换轨迹 |
| 旧 epoch 的外部 STOP | 不改指新绑定 | 拒绝陈旧当前入口；恢复用例若需停止旧执行者，显式使用保留的原绑定与授权，不能重查当前 device |

停止请求登记与普通日志工作分离。即使普通日志阻塞 / 满盘，内存中的冻结与撤销立即生效，停止效果段外走独立可用端口；尽力追加应急审计，失败明确可见。队列容量、停机和独立执行通路由后续任务实测；只有一个阻塞 SDK 线程、STOP 也排在其后面的适配器不满足这一职责。

### 7.1 已越界任务的关闭协议

1. **先止新写、先请求停止**：处理撤销并发送绑定级 STOP，不等待原 execute 返回，不先等普通日志。不知道句柄时仍可绑定级停止；不知道身份 / 目标绑定时不能猜另一台设备。
2. **关闭旧写入可能性**：取消尚可取消的队列；收敛已越界原调用；原句柄查询 / 请求查询不触发 submit。取得 writer barrier：本地任务与传输 / 下游待受理请求都已闭合，或最终写入设备确实消费且验证过的 fencing / 控制权失效证明。
3. **不能把局部事实当成 barrier**：取消 Python Future、工作线程退出、请求超时、SDK 返回、Action 客户端退出、应用新 epoch、单次句柄查询“未找到”都不自动证明旧包 / 重试器以后不会被受理。证据不足时保持锁；不以“人工确认已停”替代旧写入者处置。
4. **barrier 后再次停止并确认**：若前一 STOP 可能早于迟到提交，取得 barrier 后再向原绑定请求停止；使用该停止轮次之后、匹配设备 / 时钟 / 来源的新鲜可信反馈和完整静止窗口。barrier 前采样、仅晚到达的停车包不能用于这一轮。
5. **记录后解锁**：在同一协调序列采纳 barrier、停车与处置依据，按第 9 节保存解锁审计；写入返回后重新检查证据版本 / 身份 / 新鲜度，均仍有效才清相应 execution_blocks。任何新失效 / 运动 / 迟到写入证据都使旧解锁审计失效。

明确未下发的命令可以在不申请新停车证明的情况下结束自己的业务槽，因为它从未取得“可能执行”的物理锁；这不等于把当前 motion_state 设为 STOPPED，也不消除启动 / 外部执行者锁。已可能下发时，没有有效停车与旧写入闭合证据不得清物理锁。

普通取消走同样的写入闭合规则，区别只是控制权政策。确认取消不是新运动授权。停机、切换和恢复复用此规则，不能另开一个“强制清锁”后门。

## 8. 崩溃点与重启处理

冷启动先生成不可复用 epoch / clock_id、撤旧会话租约、DISARMED、冻结运动，保留原设备身份与 adapter 查询配置。新执行者只能查询 / 停止 / 对账，不重放日志中的计划、ticket 或意图；这里不是自动发送的 outbox。

| 崩溃点 | 本地可能事实 | 重启判定与动作 |
| --- | --- | --- |
| C0：接受记录前 | 可能无键，旧接收端存在内存预留 | 不恢复预留；先处置旧运行实例 / 写入者；旧 epoch / 期限拒新执行 |
| C1：接受写入已在途，确认未返回 | 接受记录可能有 / 无 | 检查原键与事务；没有证据不补发；候选接受不自动发布为可执行任务 |
| C2：接受记录确认，ACCEPTED 事件 / 响应前后 | 客户端可能不知已接受 | 返回原记录 / 中断事实；无意图不能由本命令合法执行，但仍核对旧执行者不能稍后提交意图 |
| C3：规划期间或计划已返回，意图前 | 接受 / 计划存在，没有执行意图 | 丢弃调度资格，不继续规划 / 执行；确定无下发的结论依赖完整日志及旧写入者闭合 |
| C4：意图写入在途或已确认，B 前 | 意图可能存在，不表示已受理 | 新实例不复用 ticket；若不能证明旧实例在 B 前被撤销，按可能执行对账 |
| C5：B 后、SDK 实际调用前 | 已取得一次性资格，可能尚未真正发送 | 本地“没看到句柄”不能证明没执行；旧线程 / 进程 / 消息全部闭合后再停车确认 |
| C6：外部调用 / 受理中，响应前 | 已发送 / 已受理与尚未受理不可仅凭本地日志区分 | 查原关联标识 / 句柄，停止原绑定；查不到仍 UNKNOWN，不再次 submit |
| C7：已受理 / 结果返回，句柄或终态保存前 | 设备可能已完成，但日志仍未结 | 原查询追加事实；不根据当前姿态追认历史成功；物理与旧写入者另处理 |
| C8：终态已保存，停止 / 解锁审计前 | FAILED / TIMED_OUT / INTERRUPTED 等业务终态可能有锁 | 终态不变，恢复执行锁 / 对账；不能只查“无 active 命令”就发新运动 |
| C9：解锁审计写入在途或已保存，清内存锁 / 激活前后 | 曾有解锁依据，不证明重启后仍新鲜 / 独占 | 新运行仍 DISARMED；重验身份、writer barrier、当前停车和审计版本；绝不恢复租约或自动激活 |

损坏、缺失或被清空的数据库不是“无未结任务”的证据。恢复只读、禁止新运动，按存储故障与原设备核验处置。幂等窗口 / 保留策略由 DEV-M1-10 声明；旧 command_id 不复用，不因窗口外查无记录就声称设备 exactly-once。

## 9. 三类事实与恢复解锁

| 事实 | 需要的证据 | 单独不能推出的结论 |
| --- | --- | --- |
| 历史结果 H | 原 command / attempt / handle、后端最终结果与当时上下文；原日志不可变 | 现在到达目标或停车，不证明过去成功 |
| 当前停车 M | 正确身份、可信来源 / 时间 / 序号、新鲜度、静止窗口、匹配停止轮次 | 不证明旧写入者 / 在途包以后不能启动 |
| 旧执行者 W | 未消费许可已撤销；已越界调用、适配器队列、传输与目标待受理动作闭合，或验证过的最终 fencing | 新 epoch、进程退出或本机锁，不自动停止或隔离旧目标动作 |

恢复解锁是显式应用用例。必要条件为：身份 / 绑定 / 证据关联正确、W 已闭合、barrier 后的停止与 M 合格、恢复操作有权限、解锁审计持久化且返回时全部证据仍有效。当前 MOVING / UNKNOWN / STALE、仅早期 STOPPED、仅应用 epoch、仅本地线程退出、句柄关联错误、审计写失败都拒绝解锁。

H 为 UNKNOWN 时可以在其他条件全部满足并经有权限的恢复处置后清当前物理执行锁，但历史 UNKNOWN 必须保留，不能改成 SUCCEEDED。反之，H 已知成功 / 失败也不能代替 M / W。解除只允许申请新的控制流程，不恢复原租约或 ARMED，更不继续原任务。

解锁采用“采纳证据 → 段外保存审计 → 回协调单元复核 evidence_revision / epoch / 身份 / 反馈年龄 → 清具体锁原因”的顺序。新运动、失效、绑定变化或证据过期必须使先前审计的解锁资格失效。审计记录至少关联原执行、writer barrier、停止轮次、停车采样窗口、操作者权限依据和处置原因。无法证明 W 的适配器只读；人工点击“已停”不能补足 W。

### 10.1 T31：调度脚本和断言

共同前提：已完成接受记录且处于 PLANNING；一个槽、无旧执行锁、原绑定明确；人工单调钟 0，默认 start_before=100、lease_expiry=1000、execution_budget=1000（单位均为模型 tick，不是设备阈值）。最终裁决是独立步骤，send 是随后可能才发生的外部尝试；这两个步骤故意分开以暴露抢占窗口。

脚本必须覆盖：STOP 在规划返回前、意图在途、任务已排队但 B 前、B 后但调用前、已受理、受理响应丢失；旧规划 / 意图 / 句柄迟到；到期等值与临界前；普通取消；重复调用资格；日志阻塞；早停车 / 只有回执 / 只有 barrier / 审计失败；完整关闭与重启后原绑定迟到调用。每种输入检查状态 / 确定性、槽、执行锁、调用 / 查询 / 停止次数、激活与租约、一次性资格及目标绑定。

主要产品屏障位置：规划返回、意图工作线程提交 / 返回、执行工作线程启动、FinalClaim 前 / 后、真实端口调用入口、受理回调、原查询返回、停止回执、writer barrier、停车窗口、解锁审计返回。测试线程按顺序显式放行；不靠高频重跑和 sleep 等概率。原调用已越界时，允许“STOP 之后才发生一次原调用”的观测，但必须保持锁并再次停止 / 对账，绝不把它报告为“旧动作已被 epoch 自动阻止”。

CANCEL_REQUESTED 只有取消证据、写入闭合与新鲜停车齐全才成为 CANCELLED；没有取消结果而仅证明当前安全时，按 H 未知的显式恢复流程处理，不能自动伪造取消成功。

### 10.2 T34：证据组合表

每个场景保存原终态与 certainty、原关联身份、writer 证据类别、停车证据类别、是否在 barrier 后停止、恢复权限与审计结果。至少分别覆盖：

- H 未知且 M / W 齐全，可审计清当前锁但保持历史；H 成功但现在 MOVING，拒绝；H 失败但 W 未解决，拒绝。
- M 缺失 / 陈旧 / 早于 barrier，或只有停止回执，拒绝；W 仅应用 epoch / 本地退出 / 句柄“未找到”，拒绝。
- 身份 / 原关联标识不匹配、恢复越权、审计失败，拒绝；日志只读不能阻断停止但不能解锁。
- 原后端结果已知但没有重新激活：清锁后仍 DISARMED、无旧租约、零重放；原终态事件不改写。

参考模型检查器拒绝未知步骤 / 字段、重复场景、非有限值与缺失必验主题；自测还要杀死“队列许可永久有效”“STOP 回执即解锁”“忽略旧写入者”“重启重放”“停车即历史成功”“忽略审计”等故意错误实现。仅删除失败场景不能让自测通过。

以下“锁定”是本次实现用工作基线，由执行角色作技术自审，不冒充独立架构评审或用户签收。变更公共语义 / 降低断言须走 CHG；实现或适配器无法满足时保持禁运动并登记缺陷，不默改条件。

| 决策 | 选择 / 结论 | 否决的替代方案 / 理由 | 复核点 |
| --- | --- | --- | --- |
| RT-D01：串行边界 | 同一 per-robot 应用协调单元裁决全部状态与 FinalClaim；外部 I/O 段外执行 | 主线程检查后让线程池随时执行，存在 STOP 穿越；持锁等待 SDK / 磁盘则阻塞停止 | DEV-M1-08 / 09；T31 真实屏障 |
