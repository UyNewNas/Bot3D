# 软件思想与范围 v0.1

- 建立日期：2026-11-19
- 更新日期：2026-11-20
- 状态：首轮设计草案；作为后续实现的工作基线，不代表硬件已选定或方案已获最终确认
- 读者：框架开发者、机器人 / 仿真适配器开发者、XR 应用开发者

## 1. 产品定义

构建一个连接虚拟交互、机器人仿真和现实设备的运行框架。上层应用使用稳定的能力、任务和状态接口；不同设备、仿真器和前端通过适配器接入。

框架不是新的机器人总线、通用物理引擎或机器人操作系统，也不承诺任意任务能在任意机器人上执行。

### 核心价值

- 应用不需要为仿真 / 真机各写一套业务流程。
- 接入新硬件时，尽量新增适配器、模型和能力配置，而非修改内核。
- XR 设备和交互引擎可替换，不反向决定硬件控制架构。
- 迁移失败可解释：明确指出缺少能力、坐标、模型、权限或时序条件。
- 实际执行状态可观测，不能以虚拟动画冒充真机反馈。

## 2. 设计原则

### P1：统一语义，不强求统一实现

“到达末端目标位姿”可以是统一能力；具体规划器、逆运动学和驱动实现不同。移动底盘、机械臂、无人机使用不同能力族，不抽象为含义模糊的同一个 move 指令。

跨机器人首先迁移任务与约束，不直接迁移关节数组、力矩或已训练策略。形态映射、技能重定向与学习迁移是后续扩展。

### P2：领域内核独立，ROS 2 优先集成

内核不导入 ROS 消息、Unity 类型或厂商 SDK。接口采用普通领域类型，ROS 2 是首个运行时适配，不是领域模型本身。

这不意味着首版同时实现多种中间件。先实现 ROS 2 路径，用依赖边界保留替换空间，不建立未经需求验证的通用插件市场。

### P3：一份事实源，分开目标与反馈

- 物理机器人状态以驱动反馈为准；仿真状态以选中的仿真后端为准。
- Unity 只渲染机器人反馈和目标预览，不再独立运行一套机器人动力学作为真值。
- 规划场景、标定、关节映射和资产版本可追踪。
- 反馈有时间戳、有效期和质量标识；过期状态不能显示成实时。

### P4：能力协商、显式降级

设备声明能力、参数范围、控制模式和限制。无能力时返回可解释错误；禁止将位置控制包装成力矩控制，禁止把停止请求已发出包装成已经停止。

### P5：控制权与环境显式

每台逻辑机器人只有一个运动控制权持有者。仿真与真机切换是受控状态变更，不是网络断开后的自动故障转移。前端始终展示 SIM / REAL、设备身份和后端代次。

### P6：非实时协调与设备闭环分离

网关、业务、XR 和 Python 运行时不承担电机硬实时闭环。控制周期、最终限位和失联策略由已验证的本地控制链处理。软件保护不是安全认证系统，物理急停独立存在。

### P7：简单部署，验证后再扩展

首版采用模块化单体加独立机器人 / 仿真进程，不引入微服务集群、消息中间件集群或多主控制。大体积传感器数据不绕道任务网关。

## 3. 范围与分期

### 框架总体范围

- 多机器人能力描述、设备注册和状态归一化。
- 仿真 / 真机适配、XR 接入、控制权与命令生命周期。
- 机器人 / 场景资产、坐标标定、日志与可回放数据。
- 扩展到移动机器人、其他仿真器和其他 XR 前端的接口边界。

### 首条验证路径的设计假设

使用固定基座单机械臂，夹爪为可选能力。先支持目标预览、末端位姿目标、执行反馈与停止，再验证同一机器人虚实切换。这只是参考垂直切片，不把机械臂写死为框架唯一类型，也不代表已选具体品牌。

先做离散目标，不在首条路径中加入连续手部跟随、力反馈、力矩控制或自主学习。真实空间先采用显式标定；实时重建、自动语义理解和跨形态技能迁移另行设计。

### 初始设计与跟踪建立的边界

- 初始设计轮和本轮跟踪建立不引入产品依赖、不交付产品运行代码；本地文档检查工具不计作框架实现。后续 M1 按迭代锁定必要依赖与工程，不把本条误读为永久禁止开发。
- 不连接真实机器人或操作硬件；[项目跟踪](../project/README.md)不自动授予安装机器人软件、Git 提交 / 推送或外部发布权限。
- 不承诺安全认证、硬实时、物理参数无损转换或通用策略迁移。
- 不选购硬件，不把供应商接口许可视为已经获得。

## 4. v0.1 架构决策

以下均为待实现和验证的工作基线，变更应记录原因。

| 编号 | 决策 | 理由 / 代价 |
| --- | --- | --- |
| D01 | 以能力和目标为前端接口，低层运动下发封装在后端适配层 | 提高语义可迁移性；需要明确能力边界 |
| D02 | 领域内核无 ROS / 引擎依赖，首个集成使用 ROS 2 | 保持可替换；增加少量类型映射 |
| D03 | 首个仿真候选 Gazebo，首个 XR 候选 Unity + OpenXR | 优先验证系统闭环，不同时接入所有工具 |
| D04 | 前端使用版本化 HTTP / WebSocket 应用接口 | 避免将 ROS 图暴露为前端公共接口；需维护小型契约 |
| D05 | 模块化单体、单实例控制权仲裁 | 降低部署和一致性复杂度；首版不提供高可用 |
| D06 | 后端绑定带代次，切换需要显式流程 | 防止旧命令落到新设备；不提供无感真机切换 |
| D07 | 控制链与传感器大数据分离 | 防止图像阻塞命令；增加独立媒体通道需求 |
| D08 | 单一执行所有者，真实状态驱动显示 | 防止 MoveIt 和驱动双重下发、双仿真真值 |
| D09 | 连续遥操作晚于离散目标执行 | 先验证控制权、时间和停止语义 |

具体模块见[技术架构](02-system-architecture.md)，数据语义见[契约](03-contracts-and-adapters.md)，验收见[实施路线](04-delivery-and-validation.md)。
